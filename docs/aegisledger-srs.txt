 1. Executive Summary & System Vision
AegisLedger v1.0 represents a financial-grade Core Banking and Double-Entry General Ledger System designed to enforce immutable transaction integrity, multi-account solvency, and zero-drift balance consistency across commercial banking operations. Modern fintech and core banking backends demand mathematical certainty: money cannot be created or destroyed, available liquidity must be strictly separated from book balances, and concurrent ledger transactions must execute with strict serializability.
The primary objective of AegisLedger is to demonstrate top-tier .NET enterprise architecture capable of powering retail deposits, commercial checking, multi-party escrow, and inter-bank clearance. By combining ASP.NET Core (.NET 10), Clean Architecture, CQRS via MediatR, EF Core Code-First with Dapper read-side optimization, SQL Server optimistic RowVersion concurrency locks, and distributed Redis idempotency protection, AegisLedger guarantees that every transaction is posted cleanly with net-zero invariant drift: SUM(Debits) == SUM(Credits).
📌 CORE BANKING SOLVENCY INVARIANT
System Solvency Rule: The system ledger enforces continuous mathematical solvency where Total Book Ledger Balance ($12,450,890.00) equals Total Available Liquidity ($12,110,230.00) plus Active Security Holds ($340,660.00). Any drift between total debits and total credits immediately triggers a global circuit breaker.

2. System Architecture & Technical Stack
AegisLedger follows a strict Clean Architecture pattern decomposed into four decoupled projects within a Modular Monolith solution structure, flanked by an enterprise Next.js Web Admin Portal and a React Native Mobile Wallet.
2.1 Solution Layering (.NET 10 Clean Architecture)
1. AegisLedger.Domain: Contains domain entities (Accounts, Transactions, LedgerEntries, TransactionHolds), Enums (AccountType, EntryType, HoldReason, TransactionStatus), Value Objects (Money, Currency), and domain invariants. Zero external dependencies.
2. AegisLedger.Application: Implements CQRS commands and queries via MediatR. Features FluentValidation pipeline behaviors, custom Exception Handling decorators, DTOs, and interface contracts for data access, Redis caching, and Hangfire background jobs.
3. AegisLedger.Infrastructure: Houses EF Core DbContext with SQL Server configuration, RowVersion optimistic locking, Dapper raw SQL query handlers for high-speed reporting, Redis cache management, and Hangfire job registration.
4. AegisLedger.Api: ASP.NET Core Minimal APIs & Controllers, JWT Bearer Token Authentication, Custom Idempotency Middleware, Serilog structured request logging, and OpenAPI / Swagger documentation.

3. Functional Requirements Specification
3.1 FR-1: Accounts & Chart of Accounts (COA) Management
The Chart of Accounts (COA) module serves as the central directory for customer deposit liabilities and system ledgers. Every account must track two distinct balances: Book Ledger Balance (total actual posted ledger funds) and Available Liquidity (book balance minus active security holds).
•	Account Types: Checking (CHK), Savings (SAV), Escrow (ESC), and System Ledgers (SYS Revenue, Assets, Liabilities).
•	RowVersion Tokens: Every account record includes a byte[] RowVersion column (e.g. 0x00000000000007D4) auto-incremented by SQL Server to detect concurrent balance modifications.
•	Solvency Metrics: Web dashboard top-bar must display real-time Total Book Ledger Balance ($12,450,890.00), Available Liquidity ($12,110,230.00), and Active Security Holds ($340,660.00).
•	Account Actions: Support for searching by account number or legal name, filtering by account type, viewing account-specific ledger journal entries, and locking/freezing accounts.
3.2 FR-2: Immutable Double-Entry Journal & Posting Pipeline
The Double-Entry Journal is an append-only ledger log where transactions generate balanced pairs of Debit (DR) and Credit (CR) posting entries. Direct modification or deletion of posted journal entries is strictly prohibited.
•	Balanced Posting Invariant: A transaction is only committed if SUM(Debits) - SUM(Credits) == $0.00 across all splits.
•	Atomic Transfer Execution: An internal transfer from Source (Debit) to Destination (Credit) creates one Transaction record and two matching LedgerEntry records inside an EF Core IDbContextTransaction with SERIALIZABLE isolation.
•	Idempotency Guarantee: Accepts X-Idempotency-Key headers (e.g., idem-cf68a6a8-35e9-48e4-7e60-b9e227108a52). Duplicate request keys within a 24-hour window return the cached response from Redis without duplicate posting.
•	Journal Reversal Mechanic: Erroneous transactions are corrected exclusively via compensating reversal entries that post equal and opposite DR/CR lines with reference to the original Transaction ID.
3.3 FR-3: Transaction Holds, Ring-Fencing & Escrow Engine
The Holds and Escrow Engine allows compliance officers and automated risk policies to ring-fence customer funds without mutating the underlying book ledger balance.
•	Hold Enforcement: Deducts the specified hold amount from Available Liquidity while keeping Book Ledger Balance unchanged.
•	Operational Reasons: Supports predefined regulatory hold reasons including 'Card Auth Pre-check', 'AML Fraud Review', 'Cheque Clearance', and 'Escrow Milestone Guarantee'.
•	Automatic Expiry TTL: Configurable time-to-live windows (30 Mins, 2 Hours, 6 Hours, 24 Hours). Upon timer expiration, Hangfire workers execute background hold releases.
•	Hold Lifecycle: States transition from Active -> Released (funds restored to Available) or Captured (funds debited permanently via journal transaction).
3.4 FR-4: Asynchronous EOD Reconciliation & Automated Hangfire Workers
AegisLedger incorporates automated End-of-Day (EOD) batch proof verification to guarantee that no historical accounting drift has occurred across the enterprise.
•	Hangfire Scheduler: Executes the EODReconciliationJob daily at 00:00 UTC (or manually triggered via administrative button).
•	Batch Verification Proof: Aggregates total system debits and total system credits, verifying a $0.00 difference across millions of historical entries.
•	Cryptographic Audit Hashes: Generates an immutable SHA-256 hash (e.g., 0x8f2a991bce4718...) representing the entire state of the ledger for that audit date.
•	Performance Logging: Logs batch execution duration (e.g., 420ms) and status in the EodReconciliationBatches table.
3.5 FR-5: Identity, Security, RBAC & Multi-Currency Switcher
•	ASP.NET Core Identity & JWT: Secure user authentication with JWT access tokens (15-min TTL) and refresh tokens stored in Redis.
•	Role-Based Access Control (RBAC): Enforces granular permissions for roles including 'Compliance Auditor', 'Bank Teller', and 'System Admin'.
•	Multi-Currency Display: Frontends provide real-time currency conversion previews across USD, EUR, and PKR using cached central bank exchange rates.
•	Correlation ID Tracking: All incoming HTTP requests and background job executions append a unique Correlation ID (e.g., corr-8f92a1b3) passed to Serilog.

7. Non-Functional Requirements (NFRs)
•	Performance & Latency: API P99 response time must remain below 15ms for transaction posting under standard loads (1,420 Txns throughput baseline). Dapper read queries must execute in <5ms.
•	Data Consistency & ACID Isolation: Transaction processing must enforce SERIALIZABLE isolation level in SQL Server to eliminate phantom reads and double-spending race conditions.
•	Auditability & Traceability: 100% of mutation operations must be captured in an append-only audit trail with request Correlation IDs, IP addresses, and user personas.
•	Resilience & Fault Tolerance: System integration points utilize Polly resilience policies implementing exponential backoff retry (3 attempts) and circuit breaker mechanics.
•	Security Compliance: Passwords hashed using Argon2id / Identity default PBKDF2; database connection strings and JWT signing keys stored in Azure Key Vault / Environment Variables.
